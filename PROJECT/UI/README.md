# UI

正式 UI 资料入口。

关联维护表：[`PROJECT/MAP/README.md`](../MAP/README.md)。该表用于持续记录 UI、业务功能、底层机制及依赖关系；不要求一次填全，也不替代本文件。

当前 APS 第一阶段正式 UI 为三页：

- **空间页**：进入和管理空间连接，并展示其中的 Context；
- **对话页**：独立 AI 对话能力；
- **设置页**：全局连接、权限与系统配置。

其中，**空间页**是 APS 面向用户的主要人机工作页面。

## 身份、层级、关系：三层分离原则

APS 软件开发结构统一遵循身份、层级、关系三层分离原则：**ID / 编码 = 我是谁；parent_id = 我现在属于谁；关系边表 = 我关联到什么。三者正交，互不推导。**

这套规则适用于目标、UI、功能、架构、施工点、Task、代码 / 产物、Verify / Evidence 等全部开发对象。

### 身份

每个对象拥有稳定、唯一、与显示名称解耦的 ID / 编码。ID 可以采用具有人类可读性的形式，例如 G-001、UI-001、FN-001、AR-001、CP-001、TK-001、CD-001。编码可以具有类似路径的可读形式，但只是编码约定，不是数据结构本身。

**ID 一旦建立，不因重命名、移动、排序或结构调整而改变。**

### 层级

节点的树形结构只能通过明确的 parent_id 表达。parent_id 只回答“我现在属于谁”。order 只负责同一 parent_id 下的兄弟节点排序，跨父节点不比较。

节点移动到另一分支时，只修改 parent_id 与同级 order，不修改 ID。

**硬规则：系统判断层级时只认 parent_id，不认 ID 的字符串形状。禁止通过拆分、截取、前缀、长度等字符串规则推导父节点。**

### 关系

功能映射、架构映射、施工关联、产物关联、验证关联等非树形关系，统一进入独立的关系边表：

```text
source_id
 target_id
 relation_type
 order
```

一个 UI 可以通过多条关系边关联多个功能、架构、施工点或其他对象；一个功能也可以关联多个 UI。关系表中的 order 只在同一个 source_id + relation_type 集合内表达顺序，不参与树形层级判断。

### 底层硬规则

```text
节点对象：id / type / name / parent_id / order / 其他属性
关系边表：source_id / target_id / relation_type / order

ID / 编码  → 身份
parent_id  → 结构归属
关系边表   → 跨对象关联
```

三者互不推导。不能因为两个 ID 有相同前缀就认为存在关系，也不能因为两个节点在 UI 上相邻就认为它们是父子。

因此 APS 的开发数据不是若干表格之间写死字段，而是“节点 / 对象 + 结构父子关系 + 关系边”的统一开发结构图。

### 关系类型与主要归属的边界

`relation_type` 用于明确关系边的业务语义。它不能被理解成新的层级，也不能替代 `parent_id`。例如可以表达功能映射、架构实现、施工关联、产物生成、验证覆盖、依赖、引用等关系；具体类型随数据模型逐步确定，但所有非树形关系都必须通过关系边表达。

Task 的 `primary_node_id`（或 `primary_construction_point_id`）表示“该 Task 主要服务于哪个结构节点 / 施工点”，属于业务归属字段，不是结构父节点。因此：

```text
parent_id
    = 节点在结构树中的父节点

primary_node_id
    = Task 的主要业务归属节点

relation edge
    = Task 与其他对象的额外关联
```

三者不可互相替代。Task 即使有主要归属，也不因此改变结构树；Task 同时关联多个结构节点时，其余关联通过关系边记录。Task 的主要结构归属使用明确的结构节点 ID；其他结构关联通过关系边记录。

**任何实现、查询、AI 上下文切片、拖拽移动、排序或 Verify 追踪，都必须沿明确关系读取，不得自行猜测关系。**

## 一、空间、连接、调度与 Context：正式定义

### 1. 空间

Space 有自己的名称。Space 内通过“目录”对 Context（项目）进行分组管理；目录不是新的业务对象层。

**空间（Space）是 APS 中负责组织目录与 Context 的基础工作空间。**

Space 属于 APS 的 Connection 体系，但它具有特殊性：**Space 不是与 AI、GitHub、File 等普通连接完全等价的连接，而是用于承载和组织地址、实际资源以及其他可组合能力的基础工作空间。**

Space 不是普通的 UI 文件夹、项目目录或个人资料区。它可以来自手机本地、PC、其他设备、云端、NAS 或未来由插件提供的其他空间。

Space 的核心组织结构为：

```
Space
├── 名称
└── 目录
    ├── Context（项目）
    │   ├── 名称
    │   ├── Address[]（名称 / 地址 / 备注）
    │   └── 可组合能力
    └── ...
```

其中：

- **Address** 回答“在哪里”，是对资源位置的定位记录；
- **Resource** 回答“实际有什么”，是 APS 可以使用、读取或操作的实际内容；
- **目录 → Context** 是 Space 内的组织层级；
- 其他能力按 Context 需要组合，不作为 Space 或 Context 的固定页面结构。

一个 Context 可以关联多个 Address，每个地址记录至少包含**名称、地址、备注**。Address 不等于 Resource。

Space 也可以具有不同的可见性或访问方式，例如个人/不公开、公开以及未来其他共享方式。这些是空间属性。

### 2. 连接

**连接（Connection）是 APS 的核心基础概念之一。**

连接是 APS 可以建立、访问、调用或管理的外部能力 / 对象。连接不等于 API，也不以某一种具体业务用途为前提。

第一阶段正式定义的 Connection 类型为：

```
Connection
├── Space
├── AI
├── GitHub
├── Local
├── File
├── Device
├── API / Service
├── Plugin
└── 未来其他连接
```

其中：

- **Space**：特殊的空间连接，同时承担连接与资源底座；
- **AI**：AI / 模型连接；
- **GitHub**：GitHub 服务及其 Repository 等资源连接；
- **Local**：Android 本地目录及本地资源连接；
- **File**：具体文件及文件资源连接；
- **Device**：手机、PC、其他设备等设备连接；
- **API / Service**：其他 API 或在线服务连接；
- **Plugin**：由插件提供的能力连接；
- **未来其他连接**：保留后续扩展空间。

因此：**空间是连接的一种，AI 也是连接的一种；GitHub、本地、文件、设备、API / 服务、插件同样属于连接体系。**

连接是统一的基础抽象；具体资源、权限、认证、能力和执行方式由对应连接类型决定。

连接不规定 APS 的具体业务用途。

### 3. 调度

**调度（Dispatcher）是 APS 的另一项核心基础能力。**

调度负责根据当前状态和任务需要组织、选择和调用连接。

```
Context
   ↓
调度
   ├── AI 连接
   ├── GitHub 连接
   ├── 本地连接
   └── 其他连接
```

APS 不要求 Context 固定绑定某一个 AI。AI 是连接，不是 Context 的固定组成部分。

### 4. Context

**Context 是 APS 的内部语义 / 数据概念，不是用户必须看到的 UI 名称。**

Context 表示空间中的一个具体工作上下文。它不预设固定的业务类型，也不要求固定包含任务、对话、验证或某一种连接。

Context 具有名称、多个可选 Address 以及按场景组合的 Connection、Task、Conversation、State、Records、Verification 等能力。不同类型的 Context 可以采用不同组合，也可以没有 Task 或某一种连接。

例如：

```
Space：APS
└── 目录：软件开发
    ├── APS（Context / 项目）
    ├── A-177（Context / 项目）
    └── 其他项目（Context / 项目）
```

这里“APS”“A-177”等都是用户自定义的显示名称；Context 是代码和数据模型使用的统一语义。UI 不要求用户使用“Context / 上下文”这个词。

Context 不限定必须是项目，也可以是游戏灵感、角色资料、旅行计划等其他用户定义的内容。

**Context 的具体显示名称完全由用户自定义。**

### Context 新建与模板

Context 不能只有“进入已有项目”的工作面，还必须提供明确的**新建 Context**入口。

新建入口属于空间页 / 目录中的 Context 管理能力，不建立独立 Project 页面。

基本入口：

```
Space
└── 目录
    ├── Context 列表
    └── ＋ 新建 Context
```

点击“新建 Context”后，第一阶段至少支持两种方式：

```
新建 Context
├── 从模板创建
└── 自定义创建
```

#### 1. 从模板创建

模板用于快速建立具有预设结构和能力组合的 Context。

第一阶段模板可以包括：

- 官方 / 内置模板；
- 用户自己的模板；
- 从已有 Context 保存的自定义模板。

模板不是固定的业务类型，也不是新的 Project 模型。模板只是 Context 创建时使用的一组默认配置。

例如：

```
软件开发模板
├── 默认 Context 字段
├── 默认 Address 类型
├── 默认能力
├── 软件开发结构
└── 其他默认配置
```

使用模板创建后，得到的仍然是普通 Context，用户可以继续修改。

#### 2. 自定义创建

用户不使用模板时，可以直接创建 Context。

最小创建信息：

- 名称；
- 备注 / 简介；
- Address；
- 需要启用的能力。

创建完成后进入该 Context 的工作面。

```
自定义创建
    ↓
名称 / 备注
    ↓
Address
    ↓
选择需要的能力
    ↓
创建 Context
    ↓
Context 工作面
```

不要求所有 Context 都具有相同能力。用户可以创建一个非常简单的 Context，也可以创建包含软件开发结构、Task、AI、GitHub、Local 等能力的复杂 Context。

#### 3. 模板必须可自定义

模板本身不能设计成不可修改的固定预设。

用户可以：

- 修改模板名称；
- 修改模板描述；
- 修改默认字段；
- 修改默认 Address 类型；
- 增加或删除默认能力；
- 修改默认的软件开发结构；
- 根据已有 Context 保存为模板；
- 基于已有模板复制后继续修改。

因此模板关系为：

```
模板
  ↓
创建 Context
  ↓
用户继续修改
  ↓
独立 Context
```

**修改模板不应反向修改已经创建的 Context。**

#### 4. 模板管理

模板管理属于 Context 创建 / 管理能力，不建立独立一级页面。

可以提供：

```
我的模板
├── 使用
├── 编辑
├── 复制
├── 从当前 Context 保存
└── 删除
```

第一阶段可以采用当前页面的展开 / 收起或简单列表交互，不需要设计复杂的模板 Dashboard。

#### 5. Context 创建后的语义

无论 Context 是：

- 直接自定义创建；
- 使用官方模板创建；
- 使用用户自定义模板创建；

最终都统一成为：

```
Space
└── 目录
    └── Context
        ├── 名称
        ├── 备注
        ├── Address[]
        └── 按需组合的能力
```

模板只参与**创建过程**，不改变 Context 的核心语义，也不成为 Context 的固定父级。


### 软件开发结构

当当前 Context 具有“软件开发结构”能力时，Context 工作面可以增加一个软件开发结构工作区域。它不是新的一级页面，也不是独立 Dashboard，而是当前 Context 的一种可组合能力。

这里的“软件开发结构”实际上由**结构树 + 施工表 + 验证关联**共同构成。三者是同一开发数据模型的不同视图，不要求采用固定的数据库表数量：

```text
结构树
目标 / UI → 功能 → 架构 → 施工点
                         ↓
                    施工卡 / Task
                         ↓
                    代码 / 产物
                         ↓
                    Verify / Evidence
```

结构树节点是**设计与组成的结构对象**，不是施工任务。第一阶段统一保留以下核心语义：

### 结构节点编码与父子分支绑定

软件开发结构中的目标、UI、功能、架构、施工点等节点，都需要拥有**稳定、唯一、与显示名称解耦的节点编码 / ID**。编码用于确定“这个节点是谁”；父节点字段用于确定“这个节点当前属于谁”。

例如 UI 树可以形成多级、多分支结构：

```text
UI-001 主界面
├── UI-001-01 空间页
│   ├── UI-001-01-01 空间列表
│   ├── UI-001-01-02 Context 页面
│   │   ├── UI-001-01-02-01 Context 概览
│   │   ├── UI-001-01-02-02 施工区
│   │   └── UI-001-01-02-03 验证区
│   └── UI-001-01-03 空间设置
├── UI-001-02 对话页
│   ├── UI-001-02-01 对话列表
│   ├── UI-001-02-02 对话窗口
│   └── UI-001-02-03 对话管理
└── UI-001-03 设置页
    ├── UI-001-03-01 连接管理
    └── UI-001-03-02 系统设置
```

上述编码可以**表达层级和分支位置**，但系统不得通过拆分编码字符串来推导父子关系。真正的结构绑定必须保存明确的父节点关系，例如：

```text
UI-001-02-02
parent_id = UI-001-02
```

因此：

- **编码 / ID**：确定节点自身身份；
- **parent_id**：确定当前结构父节点；
- **order**：确定同级节点顺序；
- **name**：用户可读名称，不参与节点身份判断。

节点名称、显示文本或路径发生变化时，不应导致节点身份改变，也不应依赖名称重新建立关联。节点移动到另一分支时，可以只改变 `parent_id` 和同级顺序，而保留自身稳定 ID。

### 多分支与跨节点关联

一个父节点可以拥有多个子节点，一个节点原则上只有一个结构父节点（根节点除外）。因此 UI 可以自然形成任意深度的多分支树，不要求所有页面、子页面使用连续或固定长度的编码。

同时，**结构父子关系与其他业务关联必须分开保存**。例如：

```text
UI-001-02-02
├── parent_id → UI-001-02
├── relation → FN-003（功能映射）
├── relation → AR-007（架构实现）
└── relation → CP-012（施工关联）
```

如果一个节点需要关联多个其他节点，则通过关系边表建立多条明确关系，而不是在节点上增加多个关系字段或把这些节点伪装成父子关系。

因此整个开发结构可以形成：

```text
目标
 ↓ 结构父子编码 / ID
UI
 ↓
功能
 ↓
架构
 ↓
施工点
 ↓
Task
 ↓
代码 / 产物
 ↓
Verify / Evidence
```

这里需要区分两种关系：

1. **结构关系**：由 `parent_id` 等明确字段表达，负责组成树；
2. **业务 / 执行关联**：由明确的节点关联 ID、Task ID、产物 ID、Verify ID 等表达，可以是一对多或多对多。

Task 的 `primary_node_id` / `primary_construction_point_id` 用于指向主要结构归属；其他涉及的结构节点通过关系边表记录，不改变 Task 的主要归属。

因此，**结构树、施工表、验证视图都通过稳定编码 / ID 关联同一套数据，但任何一个视图都不能仅凭显示层级或名称推断数据关系。**

结构节点的基础数据定义仍统一为：

- **节点身份**：稳定的节点 ID；
- **节点类型**：目标、UI、功能、架构、施工点；
- **名称**：用户可读名称；
- **说明**：该节点表达的设计 / 功能含义；
- **父节点**：用于表达结构层级；根节点可以没有父节点；
- **顺序**：同级节点的展示顺序；
- **用户确认状态**：待用户确认、已确认、已变更 / 待重新确认；
- **生命周期状态**：当前有效、已停用；停用节点保留历史关联，不直接物理删除；
- **关联项**：Task、代码 / 产物、Verify 等实际执行数据通过关联关系挂载，不直接塞入节点定义。

第一阶段默认结构为：

```text
目标
 ├── UI
 │    └── 功能
 │          └── 架构
 │                └── 施工点
 └── ...
```

这里的层级只是**默认的概念组织方式，不等于所有节点必须严格按这条父子链建立**。实际树层级只由 `parent_id` 决定；跨层或跨分支的业务关联通过独立关系边表达。上述结构是默认设计方式，不是强制限制。后续如果实际软件结构需要，同类节点可以继续细分或建立明确的关联节点，但不能为了方便施工把 Task 直接当成结构节点。

结构节点与 Task 的关系保持：

```text
结构节点
  ↓
施工点
  ↓ 1 : N
Task
  ↓
执行 / 产物 / Verify
```

**结构节点的“已确认”与 Task 的“已完成”完全不同：**

- 节点确认表示用户认可当前设计 / 结构表达；
- Task 完成表示实际施工已经满足要求并通过 Verify；
- 节点被修改后，应进入“已变更 / 待重新确认”，不能继续假定旧确认仍然有效；
- 节点确认不会自动创建 Task，也不会自动代表施工已经开始。

结构树 UI 主要负责“看懂和调整软件结构”，施工视图负责“执行工作”，验证视图负责“查看事实验证”。三者仍引用同一套节点与关联数据。

其中：

- **结构树**负责表达软件的设计与组成关系；
- **施工表**负责承载施工卡 / Task 的执行记录；
- **验证关联**负责记录 Task、代码 / 产物与 Verify / Evidence 的对应关系；
- 三者引用同一套结构数据，不建立三套互相独立的数据。

因此 UI 上可以采用：

```text
结构 | 施工 | 验证
```

作为同一数据模型的三种查看方式。

施工表不是普通的待办事项列表。施工卡必须能够关联它所在的结构节点、任务职责、执行 AI、输入资源、代码 / 产物、验证要求和实际验证结果。这里的关联统一遵循“结构父子关系 + 关系边”的模型；UI 文档不预设具体数据库表结构。

一个施工卡原则上以**一个施工点作为主要归属**；一个施工点可以挂载多个施工卡。施工卡如确实涉及其他结构节点，可以建立关联节点，但不改变其主要归属。

关系明确为：

```text
结构节点 / 施工点
      ↓ 1 : N
施工卡 / Task
      ↓ 1 : N
代码 / 文件 / 其他产物
      ↓
验证要求
      ↓
Verify 记录
      ↓
Evidence / Receipt
```

其中：

- **施工点是结构定位，不是任务本身**；
- **Task 是实际执行单位**，一个节点可以先后产生多个 Task；
- **产物属于 Task 的执行结果**，一个 Task 可以产生或修改多个产物；
- **Verify 主要关联 Task**，同时可以明确覆盖哪些产物；因此 Verify 不被设计成单纯“代码文件的属性”；
- **一个 Task 可以有多次 Verify**，例如首次失败、修复后重新验证；历史 Verify 保留，当前状态取最新有效验证结果；
- **验证要求**描述“需要验证什么”，**Verify 记录**描述“实际验证发生了什么”，**Evidence / Receipt**是实际结果证据。

因此不能用“有代码”或“AI 说完成”直接推导 Task 完成；必须经过对应的实际 Verify / Evidence。

Task 的**执行记录**与 Verify 历史需要保持区分。Task 本身是持续存在的工作单位；一次实际执行是该 Task 的一次执行尝试，不因为重新执行就自动创建新 Task。

执行记录至少需要能够表达：

- 执行所属 Task；
- 执行尝试的开始与结束；
- 本次执行阶段及实际执行 AI；
- 本次执行产生或修改的产物；
- 实际调用结果、异常或回执；
- 是否进入审查、修复或 Verify。

关系为：

```text
Task
├── 执行尝试 1
│   ├── 阶段 / AI
│   ├── 产物 / 回执
│   └── Verify 1
├── 执行尝试 2
│   ├── 阶段 / AI
│   ├── 产物 / 回执
│   └── Verify 2
└── 当前状态
```

执行尝试不是新的 Task，也不能单独决定 Task 已完成。Task 的当前状态由当前有效执行结果、子 Task 状态以及最新有效 Verify / Evidence 综合确定。

如果一次执行失败，可以继续同一 Task 进行下一次执行；如果确实形成独立的后续工作，则建立明确的子 Task 或关联 Task，而不是覆盖原执行记录。

因此需要同时保留三层历史：

1. **Task 历史**：任务本身及其结构关系；
2. **执行历史**：实际由哪个 AI、在什么阶段、进行了什么执行；
3. **Verify 历史**：实际验证过什么、结果是什么。

三者不能互相替代。

Task 的**完成判定**采用“要求满足 + 事实验证”的原则：

```text
Task
 ↓
检查自身验证要求
 ↓
检查必要子 Task
 ↓
检查当前有效产物 / 执行结果
 ↓
检查最新有效 Verify / Evidence
 ↓
全部满足 → 已完成
任一关键条件不满足 → 不得标记已完成
```

具体规则：

- Task 有明确验证要求时，必须存在覆盖这些要求的有效 Verify / Evidence，才能进入“已完成”；
- Task 没有自身验证要求、但包含必要子 Task 时，只有全部必要子 Task 满足完成条件，并形成父 Task 所需的 Evidence，父 Task 才可以完成；
- 子 Task 未完成、被取消且未被替代、或存在未解决的关键失败时，父 Task 不得标记为已完成；
- 执行记录存在异常、失败或 AI 自述“完成”，但没有满足验证要求时，Task 仍保持“待验证”或“待修复”；
- 审查通过只能表示施工结果通过审查，不能替代要求中的 Verify；
- 最新 Verify 失败会使当前 Task 回到“待修复”或“待重新验证”，历史通过记录不能覆盖当前失败；
- 新一次有效 Verify 通过后，才可以恢复“已完成”；
- 用户确认 UI 方案属于设计确认，不替代代码 / 产物的 Verify。

因此，**“已完成”是一个可由事实重新计算的状态，不是 AI 或 UI 手动写入的普通标签。**

施工卡的**阶段**与**状态**分开表达，避免把“做”“审查”“Verify”混成同一个状态字段。

建议第一阶段采用：

```text
Task 状态：
待处理 → 执行中 → 待验证 → 已完成
                  ↘
                   待修复 → 待重新验证
```

其中：

- **待处理**：Task 已建立，但尚未开始实际执行；
- **执行中**：正在进行拆分、做或审查等 Task 内工作；
- **待验证**：执行阶段已有结果，等待实际 Verify；
- **已完成**：已有满足要求的实际 Verify / Evidence；
- **待修复**：Verify 或审查发现问题，需要继续修改；
- **待重新验证**：修复已经完成，但尚未取得新的有效 Verify。

“拆分 / 做 / 审查”作为独立的**阶段字段**显示当前执行环节，例如“状态：执行中，阶段：审查”。因此“阶段”不能直接替代“状态”。

当“拆分”确实产生多个独立工作项时，允许一个 Task 建立**子 Task**，但子 Task 不是新的结构节点：

```text
施工点
  ↓
父 Task
  ├── 子 Task A
  ├── 子 Task B
  └── 子 Task C
```

规则为：

- 子 Task 默认继承父 Task 的主要施工点；如果某个子 Task 实际属于更具体的下级施工点，可以明确关联该节点；
- 父 Task 表示一项完整工作目标，子 Task 表示为完成该目标而拆出的执行单位；
- 子 Task 可以分别执行、产生自己的产物并进行自己的 Verify；
- 父 Task 不因为“子 Task 都建立了”而自动完成；需要根据父 Task 自身的验证要求，以及子 Task 的实际结果综合判断；
- 如果父 Task 只是用于组织拆分，本身没有额外验证要求，则可以在全部必要子 Task 完成并形成有效 Evidence 后进入待完成判断；
- 子 Task 的失败不会被父 Task 的状态隐藏，父 Task 应反映仍存在未解决的子 Task；
- 修复已有 Task 时不重新创建一个“替代 Task”覆盖历史记录；继续原 Task 或建立明确的修复子 Task，实际 Verify 历史均保留。

因此，“拆分”是 Task 的**结构化分解动作**，不是把原 Task 删除后换成一组无关联的新 Task。

施工卡的 UI 不需要一次展示全部历史字段，但数据模型应至少保留以下信息，并按“当前工作 / 详情 / 历史”分层展示：

**当前工作视图优先显示：**
- Task 名称；
- 主要施工点；
- 当前状态；
- 当前阶段；
- 当前负责 AI / 责任；
- 最近一次执行结果摘要；
- 最新 Verify 结果；
- 是否存在待处理子 Task；
- 最近更新时间。

**Task 详情显示：**
- Task 名称、说明；
- 主要施工点及关联结构节点；
- Task 阶段与状态；
- 拆分 / 做 / 审查责任及实际执行 AI；
- 输入资源；
- 子 Task；
- 当前及历史执行尝试；
- 代码 / 文件 / 其他产物；
- 验证要求；
- 最新 Verify / Evidence；
- 取消、关闭等生命周期信息。

**历史区域显示：**
- Task 状态变化；
- 执行尝试；
- 审查记录；
- Verify 历史；
- 产物变化及实际回执；
- 取消 / 关闭 / 重新打开记录。

因此“列表字段”只是当前工作摘要，“详情字段”用于理解任务，“历史”用于追溯事实；不能为了列表简洁而丢失历史数据。

同时，**Task 状态必须增加“已取消”**，形成：

```text
待处理 → 执行中 → 待验证 → 已完成
                  ↘
                   待修复 → 待重新验证
取消 ─────────────────→ 已取消
```

“已关闭”不作为 Task 完成状态，而作为独立的**生命周期 / 可见性信息**。这样“已完成”和“已取消”仍表达 Task 的业务结果，“关闭”只表达该 Task 是否结束当前工作面。

“删除”同样不作为 Task 状态字段，而是 UI 管理操作；默认采用隐藏 / 逻辑移除，不改变 Task 本身及其历史事实。

Task 的**取消、关闭、删除**需要与执行状态分开：

- **取消**：表示这项工作不再继续执行，是 Task 的业务状态变化；取消原因和取消时已有的执行 / 产物 / Verify 历史必须保留。被取消的 Task 不得按“已完成”计算。
- **关闭**：表示 Task 已经结束当前生命周期，通常用于已经完成或明确取消的 Task。关闭不是删除，关闭后仍可查看历史；如确有后续工作，应从原 Task 建立新的关联 Task。
- **删除**：第一阶段不采用物理删除已有执行历史的方式。UI 上的“删除”应理解为从当前工作视图中移除 / 隐藏；Task、执行尝试、产物关联和 Verify 历史仍需可追溯。涉及实际文件时，删除 Task 也不等于删除项目文件。
- **重新打开**：已关闭 Task 如果确实需要继续，不直接篡改原完成结论；应根据实际情况重新打开原 Task 或建立新的关联 Task，并保留原关闭记录及历史 Verify。

因此 Task 生命周期至少保持：

```text
创建
 ↓
执行
 ↓
待验证
 ├── Verify 通过 → 已完成 → 可关闭
 └── Verify 失败 → 待修复 / 待重新验证
                         ↓
                      再次执行
取消 ───────────────→ 已取消 → 可关闭
```

取消、关闭、删除都不能覆盖已有历史，也不能改变已经发生的实际 Verify 结果。

Verify 本身也有独立的验证结果，例如：

```text
Verify：未验证 / 通过 / 失败 / 已取消
```

Task 的“已完成”不能由“阶段 = 审查”或 AI 自述直接产生；必须满足该 Task 的验证要求并存在有效 Evidence。

“拆分 → 做 → 审查”是 Task 内的协作阶段：

```text
Task
 ↓
拆分（必要时）
 ↓
做
 ↓
审查
 ↓
Verify
 ↓
完成 / 待修复 / 待重新验证
```

其中“审查”可以发现问题并回到“做”；Verify 是最终事实验证，不能被“审查”本身替代。

**UI / 交互节点必须预留“用户确认”状态。** AI 或 APS 可以提出 UI 方案，但“已确认”只能由用户明确确认产生，不能由 AI 自行视为确认。

UI 与功能、功能与架构可以存在一对多或多对多关系；施工卡也可以关联多个代码 / 产物。实际完成状态以 Verify / Evidence 等事实依据为准。

软件开发结构不是文件目录或 GitHub 仓库目录；它是软件从设计、施工到验证的统一结构数据，而施工表正是其中的任务执行视图。

## 二、空间内部组织

Space 本身是一级工作空间；Space 内通过目录进行分组管理，目录下面放置 Context（项目）。目录只是组织结构，不承担独立业务语义。

例如：

```
Space：APS
├── 目录：软件开发
│   ├── APS（Context / 项目）
│   └── A-177（Context / 项目）
├── 目录：作品
│   ├── 作品A（Context / 项目）
│   └── 作品B（Context / 项目）
└── 目录：资料
    ├── 技术研究（Context）
    └── 灵感记录（Context）
```

“目录”是 Space 内的组织方式 / 分组结构；Context（项目）位于目录之下，不是 APS 顶层固定业务类型；名称和具体组织方式可以由用户决定。

## 三、Context 的内容边界

Context 不是固定模块的集合，而是允许多种能力组合的工作语义边界。

固定基础：

```
Context（项目）
├── 名称
├── Address[]
│   ├── 名称
│   ├── 地址
│   └── 备注
└── 可组合能力
    ├── Connection
    ├── Task
    ├── Conversation
    ├── State
    ├── Records
    ├── Verification
    └── ...
```

这里的“可组合能力”按具体 Context 类型和用户需要决定，并非全部必须存在。

例如：

- 软件开发 Context 可以组合 GitHub、Local、AI、Task、Dispatcher；
- 图片创作 Context 可以组合 Local、File、AI，也可以不使用 Task；
- 纯 AI Context 可以只使用 AI；
- 其他未来 Context 可以形成不同组合。

**Task 是工作对象，不是所有 Context 的固定组成部分。**

**AI 不属于 Context 的固定模块。** AI 是一种 Connection；是否使用 AI、使用哪些 AI，以及是否允许调用其他连接，由具体 Context 的组合和权限决定。

## 四、资源与地址

**Address 与 Resource 是两个不同概念。**

- **Address**：Context 的项目地址记录，回答“在哪里”；
- **Resource**：实际内容，回答“那里有什么”。

一个 Context 可以关联多个 Address：

```
Context（项目）
└── Address
    ├── GitHub
    │   ├── 名称：主仓库
    │   ├── 地址：owla19s-ux/APS
    │   └── 备注：主开发仓库
    ├── Local
    │   ├── 名称：本地工作区
    │   ├── 地址：/Documents/APS
    │   └── 备注：本地资料
    └── 其他地址
```

这些地址所定位的实际文件、仓库内容、资料、设备对象或其他可操作对象，才属于 Resource。

资源通过对应 Connector 访问。APS 不默认复制或同步这些资源。

因此，**Address 不是 Resource，Resource 也不是 Address；Space 的基础是目录与 Context，Context 通过 Address 定位 Resource。**

## 五、三页总览

```
APS
├─ 空间页
│  └─ 空间连接 / Context 的主要人机工作面
├─ 对话页
│  └─ 独立 AI 对话 / 查询 / 测试
└─ 设置页
   └─ 全局连接与系统设置
```

## 六、空间页

**空间页 = 用户进入、选择和管理 Space，并进入具体 Context 的主要人机工作面。**

主要展示和操作：Space、地址、资源、Context，以及当前 Context 实际组合的连接和能力。

任务、对话、状态、工作记录、验证、调度等属于可组合能力，只有当前 Context 使用或支持时才需要在 UI 中显示；不把它们作为所有 Context 都必须存在的固定区域。

Space 名称、目录名称、Context（项目）名称均由用户定义。

空间页可以展示和管理当前可用连接，例如 AI、GitHub、本地、设备、插件及其他服务。调度状态和结果也可以在此展示。

对于具备 Local 能力的 Context，空间页必须保留本地资源的实际操作入口。用户可以在 Context 工作面中通过 Local Connector：

- 选择或访问已授权的本地目录；
- 读取本地文件；
- 修改本地文件内容；
- 保存修改后的文件；
- 查看实际读取 / 修改结果及必要的验证状态。

本地文件操作不是仅用于显示文件路径，也不是简单的文件同步功能；实际读取、修改和保存必须进入 Local Connector 执行链，并以实际执行结果作为事实依据。

APS 不固定 Decision AI、Worker AI、AI A / AI B 或永久主 AI。具体由调度和连接状态决定。

AI 的口头结果不能直接作为事实状态，需要结合实际结果、验证或其他证据形成工作记录。

## 七、对话页

### 1. 定位

**对话页是 APS 的独立 AI 使用入口，不是第二个 Context 工作面，也不是一个新的 Dashboard。**

其核心用途是：

- 直接选择 / 切换一个 AI 连接；
- 进行普通 AI 对话；
- 查询、分析和测试；
- 在用户授权范围内调用其他连接；
- 查看实际调用结果及必要的验证结果。

对话页的交互母版沿用 Context 工作面中的“对话 + 输入”交互，不另造一套聊天产品式结构。

### 2. 对话管理

普通对话页不仅管理当前聊天内容，还负责普通对话本身的创建和组织。

第一阶段至少支持：

- 新建对话；
- 查看、切换已有对话；
- 重命名对话；
- 删除对话；
- 新建对话分组；
- 重命名对话分组；
- 删除对话分组；
- 将对话移动到其他分组。

对话默认自动保存，不要求用户手动点击“保存”。

对话分组只是普通对话的组织方式，不建立独立一级页面，也不增加复杂标签、智能分类等机制。

### 2.1 对话记录与项目记录的保存边界

第一阶段必须明确区分**普通对话记录**与**Context / 项目工作记录**，两者不使用同一套保存边界。

- **普通对话记录**：由 APS 默认自动保存，属于普通对话本身；没有关联 Context 时，不自动写入任何项目文档。
- **关联 Context 后的对话**：仍保留为当前普通对话记录；如果其中产生了需要进入项目工作过程的内容，可以形成 Context 的工作记录，但不因此改变普通对话记录的归属。
- **Context / 项目工作记录**：属于项目资料的一部分，应保存到该 Context 对应的本地文档 / 本地工作区，而不是保存到 APS 自身的运行日志目录。
- **项目文件、设计资料及其他由项目产生的持久化文件**：按照当前 Context 对应的本地文档 / 本地工作区保存；不因为 APS 运行而默认复制到 APS 自身数据目录。
- **APS 运行日志、崩溃日志等系统运行数据**：继续保存到设置页定义的 APS 数据目录，与项目文件和项目工作记录分开。

因此第一阶段的基本边界为：

普通对话
   ↓
APS 自动保存的对话记录

Context / 项目
   ↓
项目工作记录 + 项目文件 + 项目资料
   ↓
对应本地文档 / 本地工作区

APS 自身运行数据
   ↓
手机存储主目录 / APS/

普通对话记录不能因为“自动保存”而与项目文件混为一体；项目记录也不能因为存在对话而默认写入普通对话存储。

基本关系：

```
普通对话页
├── 对话分组
│   ├── 分组A
│   │   ├── 对话1
│   │   └── 对话2
│   └── 分组B
│       └── 对话3
└── 当前对话
```

### 3. 基本结构

手机端保持简单的单页对话结构：

\`\`\`
┌──────────────────────────┐
│ 对话                  ⋯ │
├──────────────────────────┤
│ AI：GPT-5.6 Luna      ▾ │
├──────────────────────────┤
│                          │
│ AI：……                   │
│ 用户：……                 │
│ AI：……                   │
│                          │
│ [实际连接调用 / 结果]     │
│                          │
├──────────────────────────┤
│ ＋  输入消息……       ↑  │
└──────────────────────────┘
\`\`\`

其中：

- 顶部用于当前 AI 连接及相关操作；
- 中间是当前对话记录；
- 输入区保持原版 Context 工作面的简单输入方式；
- \`＋\` 用于选择需要提供给 AI 的其他连接或资料；
- 实际连接调用和结果应能与普通 AI 回复区分。

#### GitHub 只读文件入口

普通对话页提供“GitHub 只读”入口。用户可以使用已加密保存的 GitHub 访问令牌，或输入新令牌；验证身份后，明确选择仓库（owner/name）、分支和文件路径（每行一个），也可以在同一对话框中浏览目录并添加文件路径，再读取选定文件。已有保存凭证时可在该对话框中清除本机令牌；输入新令牌并验证成功即可替换旧令牌。清除凭证同时丢弃尚未发送的一次性 GitHub 文件上下文。

- 每次最多读取用户明确选择的 5 个文件；当前仅支持普通 UTF-8 文本，单文件上限 32 KiB、单次总内容上限 64 KiB。文件按顺序读取，重复路径会被拒绝。
- 读取成功后，文件内容只附加到**下一条 AI 请求**，不写入普通对话消息或项目文件；发送失败时保留这份待用上下文，供重试使用。
- 文件内容属于外部不可信数据，不能把文件内的指令当作系统 / 开发者指令。
- 此入口只提供读取能力，不开放 GitHub 文件写入、Commit 或 Workflow 触发权限。
- 目录浏览仅列出 GitHub API 返回的普通文件和目录，用户仍需明确添加文件；真实设备上的令牌授权、私有仓库读取和完整 AI 请求链仍待验收。

不增加固定的“工作区 / 工具区 / 任务区 / Dashboard”一级页面。

### 4. AI 选择

对话页可以选择或切换 AI 连接。

AI 不被固定定义为“主 AI”“施工 AI”“决策 AI”等角色。对话页中的 AI 只是当前直接使用的 AI 连接。

如果当前 AI 无法完成某项操作，可以由用户切换其他 AI；是否允许调用其他 AI 或其他连接，取决于当前授权和连接能力。

当前对话的 AI 选择应同时明确**连接和模型**，而不是只选择一个显示名称。连接列表来自全局 AI / API 连接管理；模型列表来自当前所选连接。新建对话默认使用全局默认连接，已有对话保留自己的选择。切换连接后重新加载该连接的模型，不自动猜测替换原模型。连接不可用时提示用户测试、修复或切换，不得静默切换到另一个 AI。

### 5. 连接调用

独立对话可以按需调用：

- 本地资源；
- 云端资源；
- GitHub；
- 文件；
- 空间；
- Context；
- 其他插件或服务连接。

其中，本地能力必须明确保留**本地文件读取与修改能力**。在用户授权范围内，对话页可以通过 Local Connector：

- 读取已授权的本地目录和文件；
- 将 AI 生成或用户确认的修改写回本地文件；
- 保存修改结果；
- 返回实际执行结果，并在需要时进入验证。

调用不意味着对话页自动拥有这些连接的全部权限。

本地文件修改同样不能以 AI 回复中的“已完成”作为事实。必须以 Local Connector 的实际执行结果为准。

\`\`\`
用户输入
   ↓
AI 理解 / 决定是否需要连接
   ↓
用户授权范围内调用连接
   ↓
实际执行
   ↓
实际结果
   ↓
返回对话
\`\`\`

**AI 说“已经完成”不等于连接实际执行完成。**

### 5.1 资料选择与资源引用边界

输入区的“＋”用于把用户明确选择的连接、文件或其他资料提供给当前对话使用。**选择资料不等于复制资料，也不等于修改资料。**

第一阶段至少区分三种行为：

- **引用 / 读取**：把已授权资源提供给 AI 阅读或分析，不改变原资源；
- **生成结果**：AI 在对话中产生文字、代码或其他结果，默认仍属于当前对话内容；
- **写入 / 修改**：只有用户授权并实际调用对应 Local / File / 其他 Connector 后，才改变目标资源。

因此基本链路为：

选择资料
↓
确认当前对话可使用的资源
↓
读取 / 分析
↓
AI 生成结果
↓
如需保存为项目文件或修改原文件
↓
明确目标位置 + 授权
↓
Connector 实际写入
↓
实际结果

第一阶段不把“把文件加入对话”设计成隐式复制、隐式同步或隐式修改。用户选择的资料应保持原位置，除非明确执行写入操作。

对于项目场景，AI 生成的内容如果需要成为项目长期文件，必须明确选择或使用当前 Context 的本地文档 / 本地工作区作为保存目标；仅出现在对话消息中，不视为已经形成项目文件。



如果发生文件修改、GitHub 修改、资源写入等实际操作，应以连接返回的实际结果及必要的验证结果作为事实依据。

### 6. 与 Context 的关系

对话页**不要求预先绑定 Context**。

没有绑定 Context 时：

- 可以直接与 AI 对话；
- 可以按授权使用可用连接；
- 不自动继承任何 Context 的资源和权限。

关联 Context 后：

- 当前对话可以读取该 Context 允许访问的资源；
- 调用连接必须遵守该 Context 的权限；
- 涉及实际修改时，必须遵守 Context 对连接及操作的授权；
- 对话记录可以作为该 Context 的工作记录之一。

因此：

\`\`\`
独立对话
   │
   ├── 不关联 Context → 独立使用连接
   │
   └── 关联 Context → 遵守 Context 权限
\`\`\`

关联 Context 不意味着自动启动 Context 的三阶段任务调度。

### 7. 与 Context 工作面对话的区别

两者使用相同的基础对话交互，但入口和语义不同：

| 项目 | Context 工作面对话 | 独立对话页 |
|---|---|---|
| 入口 | Context 内 | APS 对话页 |
| 核心用途 | 当前 Context 的工作记录与处理 | 直接使用 AI |
| Context | 已经处于当前 Context | 可不关联 |
| 待处理任务 | 直接关联当前 Context 任务 | 不强制存在 |
| AI | 作为当前 Context 可用连接 | 当前直接使用的 AI 连接 |
| 多连接调用 | 由 Context 调度 / 权限约束 | 按当前授权按需调用 |
| 输入 | 原版 Context 输入 | 沿用同一输入交互 |
| 实际结果 | 记录到 Context 工作过程 | 显示在当前对话，并可形成记录 |

独立对话页不是 Context 工作面的替代品；Context 工作面也不是独立对话页的必经入口。

### 8. AI Code 权限

普通对话页提供一个可直接点击切换的 AI Code 权限按钮，用于控制当前普通对话中的 AI Code / AI 实际执行代码和操作的策略。

第一阶段只保留三级：

```
AI Code
├── 自动
├── 询问
└── 拦截
```

- **自动**：在已有授权范围内允许 AI Code 自动执行；
- **询问**：执行前要求用户确认；
- **拦截**：禁止 AI Code 执行实际操作。

该按钮属于普通对话页的当前操作控制，不放入设置页，也不作为 Context / 项目的固定权限结构。

AI Code 权限不能绕过 Android / APP 系统权限或 Connection 访问授权：

```
Android / APP 系统权限
        ↓
Connection 访问授权
        ↓
AI Code：自动 / 询问 / 拦截
        ↓
实际操作
        ↓
实际结果 / Verify
```

### 9. 第一阶段边界

第一阶段对话页只保留：

- 本地目录 / 文件读取；
- 本地文件修改与保存；

- AI 选择 / 切换；
- 对话分组与对话管理；
- 对话默认自动保存；
- 对话头像；
- 对话记录；
- 简单输入；
- \`＋\` 连接 / 资料选择；
- 实际连接调用结果；
- 必要的执行 / 验证状态。

暂不增加：

- API 角色设定 / 角色卡等复杂角色体系；
- 独立 Dashboard；
- 强制任务模式；
- 强制三阶段调度入口；
- 复杂工作流编辑器；
- 与 Context 无关的复杂项目管理功能。

## 八、设置页

**定位：全局连接与系统设置。**

设置页负责管理 APS 的全局连接、系统级权限和全局配置，不承载具体 Context 的工作过程。

### 1. 基本交互

设置页沿用 APS 当前 UI 的**点击展开 / 收起**交互，不采用独立 Dashboard 或复杂设置首页。

初始状态只显示一级设置区域：

```
┌──────────────────────────┐
│ 设置                  ⋯ │
├──────────────────────────┤
│                          │
│ 连接与服务            ›  │
│                          │
│ 权限                  ›  │
│                          │
│ 验证                  ›  │
│                          │
│ 系统                  ›  │
│                          │
└──────────────────────────┘
```

点击某个区域后，在当前页面直接展开：

```
连接与服务              ˅
────────────────────────

AI / API             ›
GitHub               ›
其他连接              ›
插件 / 服务           ›


权限                  ›
验证                  ›
系统                  ›
```

再次点击一级区域即可收起。

**原则：收起时保持简洁，展开后直接操作，不增加第二层“配置按钮”作为中间入口。**

一级区域内部也可以继续采用同样的点击展开 / 收起方式。例如点击“AI / API”后，可以直接展开已配置的 AI 连接及添加操作。

### 2. 全局连接

“连接与服务”负责管理 APS 的全局连接，包括：

- AI / API 连接；
- GitHub 连接；
- 其他全局连接；
- 插件及服务连接；
- 连接所需的认证、地址和基础配置。

展开后直接显示和管理对应连接，例如：

```
AI / API                ˅
────────────────────────

GPT-5.6 Luna             ●
Claude                   ●
其他 AI                  ○

＋ 添加 AI / API
```

AI / API、GitHub 等具体连接可以继续展开到连接详情，用于：

- 查看已连接项目；
- 增加、删除、启用或停用连接；
- 配置连接名称；
- 配置地址；
- 配置认证信息；
- 配置模型等基础参数；
- 进行连接测试。

连接在设置页完成全局配置，具体 Context 再决定是否使用以及授予什么权限。

### 2.1 AI / API 模块目标与边界

AI / API 是 APS 的基础连接层，不应只是一个填写 URL、密钥和模型的表单。它负责统一管理多个 AI 服务连接，并为普通对话、Context 对话和后续调度提供可复用的连接能力。

核心关系：

```text
AI / API 连接管理
    ├── 连接配置与凭证
    ├── Provider / 协议适配
    ├── 模型目录与模型能力
    ├── 连接测试与诊断
    └── 统一请求执行
              ↓
       对话 / Context / 调度
```

**连接、协议、模型和对话选择是不同概念，不得混成一个配置项：**

- **连接（Connection / Profile）**：一组可独立保存的服务端点与认证配置，例如某个服务商账号、自建服务或兼容接口。
- **Provider / 协议**：说明请求应采用哪一种 API 协议或兼容方式。协议适配不等于服务商名称。
- **模型（Model）**：某个连接提供的模型 ID，以及可查询或配置的能力信息。
- **对话绑定**：当前对话实际使用的连接和模型；不能只显示一个模糊的 AI 名称。
- **凭证（Credential）**：API Key、Token 或其他认证材料，独立于连接元数据管理并安全保存。

一个服务商可以有多个连接；多个服务商可以采用同一种协议；同一个连接可以提供多个模型。不能通过连接名称或模型 ID 猜测协议和能力。

### 2.2 AI / API 连接列表

点击“AI / API”后直接展开连接列表，不另建复杂 Dashboard。

列表至少显示：

- 连接名称；
- Provider / 协议类型；
- 当前默认标记；
- 启用 / 停用状态；
- 最近一次测试状态（成功、失败、未测试）；
- 当前配置的模型或模型数量。

连接列表操作：

- 新建连接；
- 打开并编辑连接；
- 复制连接配置为新连接（凭证默认不复制，避免无意共享密钥）；
- 启用 / 停用连接；
- 设为默认连接；
- 删除连接；
- 运行连接测试。

删除正在被对话或 Context 引用的连接时，应提示影响范围；历史对话仍保留当时的连接名称、模型 ID 和请求记录，不得因删除配置而删除对话内容。

### 2.3 新建 / 编辑 AI 连接

采用同一张表单完成新建与编辑，明确区分“保存配置”和“测试连接”。

字段按以下顺序组织：

1. **连接名称**：用户自定义，例如“个人 OpenAI”“自建推理服务”。
2. **Provider / 协议**：至少支持 OpenAI-compatible；架构需允许增加原生 Anthropic、Google Gemini 及其他协议适配器。自定义地址不自动等于 OpenAI-compatible，应由用户选择协议或使用明确的兼容类型。
3. **Base URL / Endpoint**：服务 API 地址；显示协议适用的地址格式和必要路径说明。
4. **认证方式**：按协议显示支持的认证方式；第一阶段至少支持 API Key / Bearer Token。认证字段随协议变化，不要求所有 Provider 共用同一种输入框。
5. **API Key / Token**：以密码字段显示，默认遮蔽；可更新或清除，不在列表、错误提示、普通日志中显示明文。
6. **模型**：可从模型目录加载并选择，也允许手动输入模型 ID。
7. **可选请求参数**：按当前协议和模型能力显示，例如 temperature、最大输出 Token、超时等；不支持的参数不应假装生效。
8. **高级选项**：仅在需要时展开，容纳自定义请求头、额外参数等，不挤占默认表单。

底部操作：

```text
[测试连接]   [保存连接]
```

- **测试连接**只执行实际测试并显示结果，不自动保存用户尚未保存的修改。
- **保存连接**只负责持久化配置，不代表连接已经可用。
- 若配置有未保存修改，离开页面或切换连接时应提示保存、放弃或取消。
- API Key 等敏感信息使用 Android Keystore 保护；元数据与密钥分开保存。导出、复制连接时默认不导出密钥。

### 2.4 模型目录与能力

模型选择属于连接详情的一部分，不建立独立一级页面。

模型目录至少支持：

- 从当前连接查询模型列表；
- 搜索和选择模型；
- 手动输入模型 ID；
- 刷新目录；
- 显示模型 ID 与可选显示名称；
- 保留用户手动配置的模型，即使服务端目录暂时不可用。

“获取模型列表”和“测试聊天请求”是两种不同操作。模型列表请求成功，不代表模型一定能够完成聊天；目录接口不支持时，允许手动输入模型并继续进行聊天测试。

每个模型可以关联能力信息，例如：

- 文本输入 / 输出；
- 流式输出；
- 工具调用；
- 图片输入；
- 音频输入 / 输出；
- 结构化输出；
- 上下文长度或输出上限（仅在来源可靠时显示）。

能力应标记为“服务端明确提供”“适配器已知”或“未知”；未知不能显示为支持。第一阶段先实现文本聊天、流式能力标记和手动模型 ID；其他能力按协议适配与实际验证逐步开放。

### 2.5 连接测试与错误诊断

连接测试必须独立于“保存”和“获取模型列表”，并在页面中显示可理解的结果。

测试至少区分：

- 地址格式或网络连接失败；
- 认证失败；
- 模型不存在或无权访问；
- 服务商限流；
- 服务端错误；
- 超时；
- 协议或响应格式不兼容；
- 测试成功。

测试过程显示“测试中”，结束后显示成功 / 失败、错误类别、必要的 HTTP 状态与可执行的下一步。详细错误可展开查看；不得在提示、日志或诊断信息中泄露 API Key、Authorization 头或其他凭证。

模型目录查询、最小聊天请求和连接健康状态分别记录，不能用其中一种成功替代其他测试结论。测试结果需要记录时间；配置发生变化后，旧的成功状态应标记为过期。

### 2.6 统一请求体验

普通对话和 Context 对话应通过统一的 AI 请求层调用连接，不直接依赖某个具体 Provider 的实现。

用户可见的请求状态至少包括：

- 等待中 / 请求中；
- 正在接收流式回复；
- 已完成并保存；
- 用户取消；
- 超时；
- 连接或认证失败；
- 限流 / 服务端失败；
- 响应解析失败。

基本交互要求：

- 默认支持流式回复；若当前协议或连接不支持，应明确降级为非流式，不伪装成流式；
- 请求中允许取消；取消后仍需准确处理已收到的内容与保存状态；
- 避免同一对话对同一连接发生未受控的并发请求；
- 超时、限流和临时服务端错误可按策略重试；重试行为和次数应可理解，不能无限重试；
- 保留必要的请求耗时、连接 ID、模型 ID、结果状态和错误类别，用于诊断；
- 默认不记录 API Key、完整认证头或其他敏感信息。

工具调用、AI 多模态、结构化输出、复杂重试策略等由统一请求层和协议适配器逐步扩展，不在第一阶段假设所有服务商都支持。

### 2.7 默认连接与对话绑定

全局默认连接只用于新建对话时的初始选择，不应覆盖用户已经为某个对话选定的连接。

每个普通对话和 Context 对话都应能明确查看 / 切换：

- 当前连接名称；
- 当前模型；
- 连接状态或不可用提示。

选择连接后，模型列表应切换到该连接可用的模型；切换连接不能继续静默使用上一个连接的模型 ID。若原模型在新连接中不存在，应要求用户选择或确认，而不是猜测替换。

建议的选择交互：

```text
当前 AI
连接：个人 OpenAI       ▾
模型：model-id          ▾
```

- 设置页管理全局连接和默认连接；
- 对话页管理当前对话实际使用的连接与模型；
- Context 可按需限定可用连接，但不固定绑定某一个 AI；
- 对话历史保留当时的连接 / 模型标识；用户切换当前模型不应改写旧消息记录；
- 如果连接被停用、删除或凭证失效，UI 应明确提示并允许切换，不得悄悄改用其他 AI。

### 2.8 AI / API 分阶段范围

UI 目标定义完整能力，但实现必须按阶段验证，不能因为页面已经预留就宣称功能已完成。

**基础闭环优先实现：**

1. 多连接新增、编辑、删除、启用 / 停用与默认选择；
2. 连接配置与加密凭证安全持久化，兼容迁移旧单连接配置；
3. OpenAI-compatible 协议适配及可扩展 Provider 边界；
4. 模型目录查询、手动模型 ID、连接测试和明确错误状态；
5. 对话级连接 / 模型选择与绑定；
6. 统一请求状态、取消和可验证的流式输出；
7. 对应的单元测试、失败路径测试和实际工作流验证。

**后续逐步扩展：** 原生 Anthropic / Gemini 等协议、工具调用、多模态、结构化输出、丰富请求参数、限流与重试策略、模型能力目录和更完整的诊断。

以上是模块目标与 UI 行为约定，不代表当前代码已经全部实现。功能地图和施工状态表应分别记录“已实现、已验证、待验证、未实现”，不得将设计目标写成已交付能力。

### 3. 系统级权限

“权限”只负责 **APS 应用本身和 Android 系统层面的权限**，不负责具体 Connection 的资源访问权限。

例如：

- Android 通知权限；
- 后台运行 / 后台活动相关权限；
- 文件 / 存储等 Android 系统授权；
- 相机、麦克风等系统能力授权；
- APS 自身需要的其他系统级权限。

**AI、GitHub、Local、File 等 Connection 的访问 / 修改权限不放在这里。**

Local 本身是一种 Connection，因此“允许 APS 访问哪个本地目录、允许读取还是修改”等属于 **Local Connection 的访问授权**，由连接使用场景和当前 Context / 对话的授权共同决定。

这样设置页的“权限”和连接权限形成明确边界：

```
设置页
└── 权限
    └── APP / Android 系统权限

Connection
├── AI
├── GitHub
├── Local
├── File
└── ...
    └── 具体资源访问 / 操作授权
```

独立对话页再通过 AI Code 权限级别控制当前 AI 是否可以执行相应代码或实际操作。

### 4. 验证能力

“验证”作为可展开的设置区域保留，但**第一阶段只保留验证能力的设置入口和概念，不实现复杂的统一自动验证机制。**

原因是不同连接的“完成证明”方式不同。GitHub、文件、本地资源、API、设备等连接，其实际结果和可验证证据并不统一，当前阶段不应为了统一界面而强行设计一套不可靠的自动验证系统。

展开后保持简单：

```
验证                  ˅
────────────────────────

验证能力
暂未启用复杂自动验证

说明：
不同连接的实际结果和验证方式不同，
后续根据具体连接逐步增加。

后续扩展
```

当前阶段不要求用户配置复杂的验证规则，也不要求 APS 对所有连接自动判断“是否真正完成”。

具体执行结果仍应区分：

```
AI / 连接返回
      ↓
实际执行结果
      ↓
验证（第一阶段暂不强制统一自动化）
```

因此：

- AI 的口头“完成”不能直接作为事实；
- 有明确实际结果时，优先展示实际结果；
- 暂时无法可靠验证时，不伪造“已验证”；
- 后续可以针对具体连接逐步增加可靠的验证方式。

验证机制属于后续扩展能力，当前不作为第一阶段核心功能实现。

### 4. AI Code 权限级别

**第一阶段 AI Code 三级控制只属于普通对话页，不放入 Context / 项目工作面。**

该按钮用于控制当前 AI Code / AI 实际执行代码和操作时的权限级别，不放入设置页。

按钮采用三个视觉状态表示三个策略。用户点击按钮即可在三个策略之间切换；当前策略必须始终在按钮本身可见，不要求进入设置页才能确认。

第一阶段固定为：

```
AI Code
├── 自动
├── 询问
└── 拦截
```

三个颜色是权限状态的视觉标识，不把颜色本身当作权限语义；实际权限规则由 APS 的权限模型定义。

该按钮只出现在：

- **独立对话页**：控制当前普通对话中 AI Code 的执行策略。

Context / 项目工作面第一阶段不增加 AI Code 三级按钮。

切换策略时必须立即更新当前对话的权限状态。涉及本地文件、GitHub 或其他 Connection 的实际操作时，仍必须同时满足对应 Connection 的访问授权；**AI Code 策略不能绕过 Connection 权限或 Android 系统权限。**

因此权限链为：

```
Android / APP 系统权限
        ↓
Connection 访问授权
        ↓
AI Code 权限级别
        ↓
实际操作
        ↓
实际结果 / Verify
```

AI Code 策略是当前普通对话的执行控制，不替代 Connection 的授权，也不替代 Verify。

### 5. 本地 APS 数据目录

APS 默认在 Android 手机**内部共享存储的根目录（手机存储主目录）**中自动创建 `APS/` 文件夹，用于保存 APS 自身产生的运行数据。

例如：

`/storage/emulated/0/APS/`

第一阶段固定要求：

- 默认位置就是手机存储主目录；
- `APS/` 位于 Android 公开、用户可访问的共享存储区域；
- **不得默认创建在 `/data/` 或其他应用私有目录**；
- 不要求用户另外选择或手动创建 `APS/` 文件夹；
- APS 首次需要写入运行数据时自动创建该文件夹及其子目录；
- 用户可以通过 Android 文件管理器等方式访问、查看和管理其中的数据。

建议结构：

```
APS/
├── logs/
│   ├── runtime/
│   ├── collaboration/
│   ├── execution/
│   ├── api/
│   └── github/
└── crash/
```

当前保留 6 类日志：

- **运行日志（runtime）**
- **协作日志（collaboration）**
- **执行日志（execution）**
- **API 日志（api）**
- **GitHub 日志（github）**
- **崩溃日志（crash）**

其中前 5 类属于运行日志分类，崩溃日志独立保存。

日志按现有实现继续保持分类和按日期记录方式；崩溃日志单独按崩溃事件保存。

`APS/` 是 APS 自身运行数据目录，不是：

- Context 工作目录；
- 用户资料目录；
- GitHub 同步目录；
- 项目文件目录。

因此，用户选择的本地可访问目录只是 APS 数据目录的存放位置，APS 负责在其中创建和管理 `APS/`。

### 5. 系统设置

“系统”作为可展开的设置区域，用于管理 APS 本身的通用系统设置，例如：

- 通知；
- 外观；
- 不同系统导航方式下的界面适配；
- 其他全局系统设置。

系统设置同样采用点击展开 / 收起，不单独设计复杂 Dashboard。

### 6. 设置页边界

设置页负责：

```
设置
├── 连接与服务
│   ├── AI / API
│   ├── GitHub
│   ├── 其他连接
│   └── 插件 / 服务
├── 权限
├── 验证
└── 系统
```

这些内容都是 APS 全局配置。

以下内容不放入设置页：

- 具体 Context 的工作任务；
- Context 内 AI 的拆分 / 做 / 审查权限；
- Context 的具体工作记录；
- Context 专属资源操作；
- 强制三阶段任务入口；
- 独立 Dashboard。

设置页与 Context 工作面的关系保持：

```
设置页
  └── 全局连接 / 全局权限 / 系统配置
          ↓
Context 工作面
  └── 使用哪些连接 + 授予哪些 Context 权限
```

## 九、页面边界

```
                    APS
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
        空间页      对话页      设置页
          │          │           │
       空间连接      AI连接      全局连接
          │
       Context
          │
    连接 + 调度 + 内容
```

UI 页面只是 APS 的人机表现层，不重新定义 APS 的核心语义。

## 十、已废弃的 UI 模型

以下模型不再作为 APS 当前 UI 的正式概念：

- Project 作为 APS 顶层 UI 概念；
- Project Address 作为空间唯一地址；
- 一个 Project 对应一个主要资源地址；
- 空间 = 一个 Context；
- Context = 空间名称；
- AI 作为 Context 的固定组成部分；
- Decision AI / Worker AI / AI A / AI B 等固定角色分类；
- 工作区作为独立一级业务页面；
- 通过 AI 角色直接定义决策 / 施工职责；
- 复杂 Project Dashboard。

“项目”可以是用户自定义的 Context 名称，也可以用于描述一种组织方式，但不是 APS 的固定顶层 UI 概念。

## 十一、UI 与语义层的固定映射

当前正式 UI 的核心层级不是“Space 直接展开成 Context 工作面”，而是：

```text
空间页
└── Space
    └── 目录
        └── Context（项目）
            ↓ 点击
        Context 工作面
```

Context 是用户实际工作的项目单元。进入 Context 后，不再继续把“Context / 项目 / 工作区”拆成多个一级页面，而是在一个主要工作面中按需展开能力。

## 十二、Context 工作面正式结构

### 1. 页面母版

```text
┌──────────────────────────┐
│ 项目名称             ⋯   │
├──────────────────────────┤
│ 项目简介 / 备注（可选）  │
│                          │
│ 地址                  ˅  │
│  主仓库 → ...             │
│  本地工作区 → ...         │
│  资料 → ...               │
│                          │
│ 当前工作                 │
│  待处理任务 / 执行状态   │
│                          │
│ 对话                     │
│  AI：……                   │
│  用户：……                 │
│                          │
├──────────────────────────┤
│ ＋  输入消息……       ↑   │
└──────────────────────────┘
```

这是第一阶段的核心 Context UI 母版。

**名称、备注、Address 属于 Context 本身；任务、对话、AI、调度、验证等属于按需组合的工作能力。**

因此不能把“连接 / 配置 / 地址 / 任务 / 对话”全部理解成 Context 的固定数据层级。

### 2. Context 顶部信息

顶部只承担当前项目身份识别：

- Context 名称；
- 可选备注 / 简介；
- 当前目录位置；
- 更多操作。

Context 名称由用户定义。

备注属于 Context 本身，用于记录项目说明、用途、注意事项等，不等同于 Address 备注。

### 3. Address 区域

Address 是 Context 的项目地址列表。

收起：

```text
地址                         ›
3 个地址
```

展开：

```text
地址                         ˅

主仓库
GitHub · owla19s-ux/APS
备注：主开发仓库

本地工作区
Local · /Documents/APS
备注：本地源码

项目资料
File · /Documents/APS/docs
备注：设计资料

＋ 添加地址
```

每个 Address 至少包含：

- 名称；
- 地址；
- 备注。

Address 可以有类型，例如 GitHub、Local、File、Device、URL 等，但类型不是地址本身。

Address 只负责定位，不直接等同于 Resource。

### 4. Context 能力区域

Context 需要使用的能力按需出现，不建立固定的“资源 / 连接 / 任务 / 记录”一级导航。

例如软件开发 Context 可以出现：

```text
当前工作
软件开发结构
任务 / 调度
连接与权限
```

普通资料 Context 可以只有：

```text
地址
资料
对话
```

因此 Context 工作面是**一个主要工作面 + 多个可展开能力区域**，而不是 Dashboard。

### 5. 连接、AI 成员与任务职责

连接配置可以作为一个可展开区域：

```text
连接与权限                  ›
AI：3    GitHub：1    Local：1
```

展开后分别管理三类不同内容：

- **Context 可使用的 Connection**：决定 Context 可以访问哪些 AI、GitHub、Local、File 等连接；
- **AI 成员**：从当前可用的 AI Connection 中选择 / 添加当前 Context 可以使用的 AI；
- **任务职责**：为 AI 成员设置“拆分 / 做 / 审查”等任务职责；
- **连接授权**：决定具体 Connection 是否允许当前 Context 实际访问或执行。

其中：

- “拆分 / 做 / 审查”是**任务职责**，不是 AI 的系统权限；
- 一个 Task 可以分别为“拆分”“做”“审查”指定不同的 AI 成员；不要求同一个 AI 贯穿全部阶段；
- 同一阶段也可以由多个 AI 协作，但应明确各自承担的职责范围，避免多个 AI 对同一结果产生不可区分的写入；
- Task 创建时可以先指定职责要求，再由调度或用户从具有对应职责的 AI 成员中选择实际执行者；
- AI 是否实际执行过某阶段，以实际调用结果 / 记录为准，不能仅依据任务分配状态判断；
- “审查”负责检查施工结果并提出通过或修复意见；审查本身不等于 Verify，也不能直接把 Task 标记为完成；
- “Verify”可以由独立的验证机制或指定的验证执行者完成，不要求与“做”或“审查”使用同一个 AI。

因此，一个 Task 的职责分配可以表达为：

```text
Task
├── 拆分：AI-A
├── 做：AI-B
├── 审查：AI-C
└── Verify：独立验证
```

如果不需要拆分，也可以直接从“做”开始；如果修复后重新执行，则可以再次进入“做 → 审查 → Verify”，保留此前的执行与验证记录。
- AI 成员拥有某项任务职责，不代表它因此获得 GitHub、Local、File 等连接的访问权；
- Connection 授权与任务职责分别判断，二者不能互相替代；
- AI 成员也不是 Context 的固定身份，不应在 UI 中显示为“主 AI / Worker AI / 决策 AI”。

因此 Context 内的实际执行至少遵循：

```
AI 成员
   ↓
任务职责是否允许
   ↓
Connection 是否已授权
   ↓
实际调用
   ↓
实际结果 / Verify
```

### 6. 当前工作

“当前工作”只在 Context 存在 Task 或正在执行的工作时出现。

对于软件开发 Context，“当前工作”优先展示当前施工卡 / Task 的执行状态，并在任务具备验证要求时显示对应 Verify 状态，例如：

```text
当前工作
正在处理：整理 APS 文档
阶段：做
AI：GPT-5.6 Luna
产物：已生成
Verify：待验证
状态：执行中
```

任务完成状态应以实际验证结果及其他必要 Evidence 为依据，而不是仅以 AI 的口头结果为依据。

### 6.1 项目记录与项目文件

Context 的工作结果不能只停留在 UI 消息或 AI 回复中。需要长期保留的项目内容，应进入当前 Context 对应的本地文档 / 本地工作区。

包括但不限于：

- 项目工作记录；
- 设计与方案资料；
- 施工记录；
- 实际执行结果的持久化记录；
- 项目产生的其他需要长期保存的文件。

这里的“保存到对应本地文档”指保存到当前 Context 已配置或用户指定的 Local / File 资源位置，不等于复制到 APS 自身的 APS/ 运行数据目录。

如果 Context 没有可写的本地资源，则不能把“已经形成项目文件”视为已经保存成功；UI 应区分“生成 / 返回结果”和“实际写入本地文件”的状态。

Context 的项目记录与普通对话记录保持边界：普通对话仍由 APS 自动保存，只有明确形成项目工作记录或项目文件时，才进入项目对应的本地文档。



例如：

```text
当前工作                    ˅

正在处理：整理 APS 文档
阶段：做
AI：GPT-5.6 Luna
状态：运行中
```

没有任务时不强制显示空任务面板。

任务完成后，结果可以进入 Context 的工作记录，但不能因为存在历史记录就把“记录”变成固定一级页面。

### 7. 对话与输入

对话是 Context 的一种工作能力。

保留简单的：

```text
对话消息
    ↓
输入
```

不额外建立“聊天 Dashboard”。

Context 对话与独立对话页使用同一基础交互母版，但语义不同：

- Context 对话：属于当前项目工作过程；
- 独立对话：不要求绑定 Context。

### 8. 软件开发结构

软件开发 Context 可以在当前工作面增加：

```text
软件开发结构              ›
```

展开后可以从**结构树、施工表、验证视图**等角度查看同一套开发数据，不建立多套互相独立的数据。

核心关系为：

```text
目标
 ↓
UI / 交互
 ↓
功能
 ↓
架构
 ↓
施工点
 ↓
施工卡 / Task
 ↓
代码 / 产物
 ↓
Verify
```

其中：

- **结构树**回答“这个软件由什么目标、功能、架构和施工点组成”；
- **施工表 / Task**回答“现在具体要做什么、由谁负责、做到什么状态”；
- **验证 / Verify**回答“这个 Task 及其产物是否实际成立”。

因此，**Task 与 Verify 高度关联，但二者不是同一个对象**。一个施工卡 / Task 应能够关联其代码、文件或其他产物，并关联对应的验证要求与实际验证结果。

任务状态不能仅依据 AI 返回“完成”确定。至少应形成：

```text
Task
 ↓
执行
 ↓
代码 / 产物
 ↓
Verify
 ↓
Evidence / Receipt
 ↓
任务完成状态
```

Verify 失败时，Task 不应被 UI 直接标记为“已完成”；应保持失败、待修复或待重新验证等可判断状态。

“结构 | 施工 | 验证”是**同一开发结构的不同查看方式**，不是三个彼此独立的工作系统。

这仍然属于当前 Context，不建立新的 Project 页面或 Dashboard。

### 9. 用户确认

软件开发结构中的 UI / 交互节点必须保留：

```text
UI / 交互方案
    ↓
待用户确认
    ↓
已确认
    ↓
施工
    ↓
Verify
```

“用户确认”和“Verify”分别回答：

- 用户确认：这个 UI 是不是用户要的；
- Verify：实际实现是否成立。

二者不能互相替代。

### 10. 页面退出与返回

从 Context 返回时回到：

```text
Space
└── 当前目录
    └── Context 列表
```

不进入新的 Dashboard，也不产生独立的 Project 页面。

## 十三、软件开发结构的 UI 确认位置

软件开发结构中的 **UI / 交互** 不等于“已经被用户认可的界面”。建议至少保留以下状态：

```text
UI / 交互方案
   ↓
待用户确认
   ↓
用户确认
   ↓
进入施工 / 实现
```

其中：

- **待用户确认**：AI / APS 已提出方案，但用户尚未明确认可；
- **已确认**：用户明确确认该 UI 方案，可以作为后续施工依据；
- **已变更 / 待重新确认**：确认后的方案发生实质变化，需要再次取得用户确认。

该确认状态与后面的代码 Verify 不同：**用户确认回答“这个界面是不是用户要的”，Verify 回答“实际实现是否成立”。**

第一版 UI 可以不实现完整的审批页、确认弹窗或版本管理，但必须在结构数据和 UI 中预留该位置。

- **第一阶段不扩展超过“拆分 / 做 / 审查”的任务职责模型。**

## 十五、当前核心语义原则

当前 UI 文档以以下原则作为后续设计的基础：

> **Space 负责组织；Context 负责项目；Address 负责定位；Resource 负责实际内容；能力按 Context 组合。**

具体而言：

1. **Space 是承载连接与资源的基础工作底座；**
2. **Space 的核心组织结构是目录 → Context；Context 通过 Address 定位 Resource；**
3. **Address 表示定位，Resource 表示实际内容；**
4. **一个 Context 可以拥有多个 Address；**
5. **Connection 是访问、调用或管理资源与能力的统一抽象；**
6. **Context 不固定绑定某一种业务结构；**
7. **Task、Conversation、State、Records、Verification、AI 等均按需要组合，不默认全部存在；**
8. **UI 应根据当前 Context 实际具备的能力动态呈现，而不是把可选能力写死为固定页面结构。**

## 十六、资源引用与文件操作边界检查结果

当前 UI 审查进一步固定以下边界：

| 用户动作 | 含义 | 是否改变原资源 |
|---|---|---|
| 在“＋”中选择资料 | 为当前对话提供已授权资源 | 否 |
| AI 读取 / 分析资料 | 使用资源内容 | 否 |
| AI 在对话中生成结果 | 产生对话内容 / 临时结果 | 否 |
| 保存为项目文件 | 写入 Context 对应本地文档 / 本地工作区 | 是，针对目标文件 |
| 修改已有文件 | 通过 Connector 写入目标资源 | 是 |
| GitHub / 云端写入 | 通过对应 Connector 操作远端资源 | 是 |

因此“资料引用”“对话结果”“项目文件”“资源修改”四者不再混为一个概念。

第一阶段 UI 不需要增加独立的文件工作台；文件操作继续通过当前 Context / 对话中的资源选择和 Connector 执行入口完成。真正需要持久化的项目内容必须有明确保存目标和实际写入结果。

## 十七、记录与文件保存边界检查结果

第一阶段固定采用以下保存边界：

| 内容 | 默认归属 | 默认保存位置 |
|---|---|---|
| 普通对话记录 | 普通对话 | APS 对话数据 |
| 关联 Context 的普通对话 | 普通对话 | APS 对话数据；需要形成项目记录时另行写入项目文档 |
| Context / 项目工作记录 | 项目 | 对应本地文档 / 本地工作区 |
| 项目设计、资料、产物等文件 | 项目 | 对应本地文档 / 本地工作区 |
| APS 运行日志 | APS 系统 | APS/ |
| APS 崩溃日志 | APS 系统 | APS/crash/ |

其中：

1. **普通对话自动保存，不等于自动保存到项目目录。**
2. **项目记录和项目文件需要明确写入对应的本地文档 / 本地工作区。**
3. **APS/ 目录只保存 APS 自身运行数据，不作为项目资料目录。**
4. **AI 返回“已保存”不能替代实际文件写入结果。**涉及项目文件持久化时，必须以实际 Local / File Connector 写入结果为准。
5. **GitHub、云端或其他 Address 只是资源定位方式。**不因存在 Address 就默认产生本地副本；只有明确的本地资源保存操作才形成对应本地文件。

这一边界作为后续 UI、数据模型和存储实现的共同前提，不再把“对话记录 / 项目记录 / APS 运行日志”混为一个记录系统。
